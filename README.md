# 러브맵츄얼리

함께 다녀온 곳에 각자 리뷰를 남기면, 그 기록이 다음에 갈 곳을 고릅니다.

SKALA 8주차 웹 서비스 설계 Mini-project 결과물입니다.

## 왜 만들었는가

데이트 기록은 흩어져 남습니다. 사진은 갤러리에, 후기는 대화방에, 가고 싶은 곳은 저장함에 있습니다.
흩어져 남으니 "우리 둘한테 이 집은 몇 점인가"에 답할 데이터가 안 생기고,
그 기준이 없으니 다음에 갈 곳을 매번 검색부터 시작하며, 그 빈자리를 익명 다수의 평균 별점이 채웁니다.

그래서 이 서비스는 **모든 데이터를 커플이 아니라 개인 단위로** 받습니다.
두 사람의 평가를 수식으로 합치지 않고, 각자 남긴 것을 각자의 것으로 둔 채 겹치는 곳과 갈리는 곳을 보여 줍니다.

## 핵심 설계 네 가지

**하나. 만족도를 묻지 않고 답을 두 개 받습니다.**
리뷰 한 문장에서 `fact`(이 가게가 어느 쪽인가)와 `want`(이 사람은 어느 쪽을 원하는가)를 따로 뽑습니다.
"매워서 좋았다"와 "안 매워서 좋았다"가 만족도만으로는 같은 값이 되는데, 두 값을 받으면 갈라집니다.
근거 문장을 못 자르면 그 값은 비웁니다. 추측해서 채우지 않습니다.

**둘. 환각을 프롬프트가 아니라 구조로 막습니다.**
추천에서 후보를 고르는 것은 SQL과 알고리즘이고 LLM은 이유 문장만 씁니다.
월간 리포트에서도 숫자는 전부 SQL이 세고 LLM은 문장만 씁니다.
리포트가 가리키는 장소는 서버가 입력 집합과 대조해 밖이면 버립니다.
리뷰 원문에 "이전 지시를 무시하고"를 심어 실제로 호출해 봤고, 지어낸 장소는 출력에 나오지 않았습니다.

**셋. 상태 코드는 DB 제약에서 나옵니다.**
`409`가 붙는 자리는 전부 UNIQUE 제약이 있는 자리입니다.
같은 날 같은 장소 중복은 `UQ (user_id, place_id, visited_on)`, 같은 달 리포트 중복은 `UQ (group_id, report_month)`입니다.
예외 처리를 코드 곳곳에 흩지 않고 제약 하나에 모았습니다.

**넷. 정규화를 깬 세 곳은 전부 조회 경로 위입니다.**
`place_tags`, `user_tags`, `group_places`는 `review_tags`에서 언제든 다시 셀 수 있는 파생입니다.
리뷰 저장과 같은 트랜잭션에서 갱신하고, 더하지 않고 다시 셉니다.
캐시를 둔 이유가 조회를 가볍게 하려는 것이므로 갱신은 쓰기 쪽에서 끝냅니다.

## 무엇을 할 수 있나

한 바퀴가 이렇게 돕니다.

**1. 장소를 지도에 올립니다.** 검색하면 우리 DB와 카카오 결과를 합쳐 보여 주고, 고른 곳이 핀으로 남습니다.
아직 아무도 리뷰를 쓰지 않은 곳은 회색 "기록 전" 핀입니다.

**2. 각자 리뷰를 씁니다.** 별점과 방문 날짜와 문장 하나를 남기면, 그 문장에서 태그를 뽑아 바로 보여 줍니다.
가게가 어느 쪽인지(`fact`)와 본인이 무엇을 원하는지(`want`)가 따로 붙습니다.

**3. 핀 색이 바뀝니다.** 두 사람이 다 쓰면 둘 다 좋아했는지, 갈렸는지, 둘 다 아쉬웠는지가 색으로 드러납니다.
상대의 리뷰는 내가 쓴 뒤에 열립니다. 먼저 본 쪽으로 끌려가지 않게 하려는 것입니다.

**4. 취향이 쌓입니다.** 리뷰가 쌓이면 두 사람의 `want`가 겹치는 축과 갈리는 축이 나옵니다.
"둘 다 조용한 곳", "매움은 갈림" 같은 형태입니다.

**5. 추천을 받습니다.** 협업 필터링과 태그 방향 일치를 섞어 순위를 매기고,
한 사람이라도 싫어할 곳은 떨어뜨린 뒤 남은 것을 평균으로 세웁니다.

**6. 월말에 리포트를 받습니다.** 숫자는 전부 SQL이 세고 LLM은 문장만 씁니다.
무료 그룹은 잠겨 있고 `402`로 막힙니다. 결제는 Mock 승인입니다.

## 구조

```
브라우저 (Vue 3, Vite, Pinia, 카카오 지도 / Leaflet 폴백)
      |
Spring Boot 3.5 (Controller - Service - Repository)
      |            |                |
      |     AiClient        ReportWriter      PaymentClient
      |     매칭표 -> LLM     OpenAI / 템플릿    Mock 승인
      |     (하이브리드)
      |
      +-- RecommendationClient --> FastAPI 추천 엔진 (numpy)
      |                            협업 필터링, 태그 매칭, 그룹 합의
      |                            엔진이 없으면 규칙 폴백
      |
PostgreSQL 17 (17개 테이블, Flyway)
```

태그 추출은 매칭표가 먼저 훑고 남은 문장만 LLM으로 보냅니다. 호출 수를 줄이면서 표현의 폭은 열어 둡니다.
추천 경로에는 LLM이 없습니다. 순위는 전부 수식으로 나오므로 왜 이 순서인지 설명할 수 있습니다.
지도도 마찬가지로 갈아 끼웁니다. 화면은 지도 엔진 인터페이스만 알고, 카카오 SDK를 못 불러오면
타일 없는 Leaflet 엔진으로 떨어집니다. 키가 없거나 오프라인이어도 핀과 좌표는 그대로 동작합니다.

## 실행

```bash
scripts/demo-up.sh
```

DB 확인, 백엔드, 추천 엔진, 프론트를 차례로 띄웁니다. 로그는 `.demo-logs/`에 쌓입니다.
데모 데이터를 처음 상태로 되돌리려면 다음을 실행합니다.

```bash
scripts/seed-demo.sh
```

내리는 것은 `scripts/demo-down.sh`입니다.

DB를 처음 만들 때는 이렇게 합니다.

```bash
createuser -s lovemaptually
psql -d postgres -c "ALTER USER lovemaptually PASSWORD 'lovemaptually'"
createdb -O lovemaptually lovemaptually
```

### AI 구현 바꾸기

태그 추출 구현은 `AI_CLIENT` 환경변수로 고릅니다. 구현을 모두 빈으로 올려 두고 이름으로 하나를 씁니다.

```bash
AI_CLIENT=hybrid OPENAI_API_KEY=sk-... scripts/demo-up.sh
```

| 값 | 동작 |
| --- | --- |
| `matching` | 매칭표만 씁니다. 시연 기본값입니다 |
| `hybrid` | 매칭표가 훑고 남은 문장을 LLM으로 보냅니다. `OPENAI_API_KEY`가 있어야 합니다 |
| `failing` | 태그 추출이 항상 실패합니다. 리뷰는 그대로 저장되는지 보는 용도입니다 |

## 테스트

```bash
cd backend    && ./gradlew test     # 52개
cd recommender && uv run pytest      # 38개
cd frontend   && npm test           # 144개
```

백엔드는 Testcontainers로 진짜 PostgreSQL 17을 띄워 돕니다. H2로 바꾸면 JSONB와 enum이 달라져
통과해도 믿을 수 없기 때문입니다. API 계약은 Postman 컬렉션으로도 훑습니다.

```bash
newman run postman/lovemaptually.postman_collection.json \
  -e postman/lovemaptually.postman_environment.json
```

## 폴더

| `backend/` | Spring Boot API. 마이그레이션과 엔티티, 서비스, 계약 테스트. **실행 대상은 이쪽입니다** |

## 지시되지 않았지만 한 것

- **계약 테스트 전수** 명세의 엔드포인트별 상태 코드 조합을 MockMvc와 Testcontainers로 확인합니다.
- **협업 필터링을 직접 구현** 라이브러리 없이 피어슨 상관을 numpy로 계산하고, 설계 문서의 손계산 예제를 그대로 테스트로 넣었습니다.
- **AI 실패 경로 시연** `app.ai.client=failing`으로 띄우면 태그 추출이 항상 실패하는데 리뷰는 저장됩니다.
- **추천 엔진 폴백** 엔진을 내려도 태그 점수만으로 추천이 나갑니다. 화면은 멈추지 않습니다.
- **LLM 실호출 검증** 월간 리포트를 실제로 호출한 결과를 `docs/ai-validation/`에 남겼고, 리뷰 본문에
  지시문을 심는 프롬프트 인젝션도 실제로 시험했습니다.
- **Postman 컬렉션 전수** 요청 58개와 검증 243개로 모든 엔드포인트를 훑습니다. `verify-collection.py`가
  컨트롤러를 파싱해 빠진 엔드포인트가 없는지 스스로 확인합니다.
- **AI 구현을 갈아 끼울 수 있게** 매칭표와 하이브리드와 실패 구현을 모두 빈으로 올려 두고
  `AI_CLIENT` 하나로 고릅니다. 실패 경로를 코드 수정 없이 시연할 수 있습니다.
- **두 실행 모드** 프론트는 백엔드 없이도 도는 local 모드를 유지합니다.

## 한계

- **태그 추출의 기본값은 매칭표입니다.** LLM 분기는 붙어 있고 실제로 호출되지만, 근거 없는 태그를 만드는
  경우가 남아 있어 시연은 매칭표로 돕니다. `app.ai.client=hybrid`로 바꾸면 LLM 분기가 켜집니다.
- **협업 필터링은 배치가 아니라 시드 스크립트가 채웁니다.** 스케줄러가 없어서, 오늘 쓴 리뷰는 태그 점수에는
  즉시 반영되지만 협업 필터링에는 유사도를 다시 계산해야 반영됩니다.
- **결제는 Mock입니다.** 승인 응답을 흉내 낼 뿐이고 실제 PG 연동은 `PaymentClient` 구현체 교체입니다.
- **리뷰 수정과 삭제는 이번 범위 밖입니다.** 저장과 조회까지만 만들었습니다.
- **추천 이유는 규칙 문장입니다.** 어떤 태그가 얼마나 맞았는지로 조립하며 LLM이 쓰지 않습니다.
  설명 가능성을 택한 결과이고, 문장이 다양하지 않다는 것이 그 대가입니다.

## Docker로 띄우기

로컬에 JDK, Node, uv, PostgreSQL을 따로 깔지 않고 Docker만으로 전체 스택을 띄울 수 있습니다.
저장소 루트에서 한 줄이면 DB, 백엔드, 추천 엔진, nginx가 서빙하는 프론트가 모두 올라옵니다.

```bash
docker compose up -d --build
```

포트는 로컬 개발 스택(`scripts/demo-up.sh`)과 겹치지 않게 밀어 두었습니다.
프론트 http://localhost:5174, 백엔드 http://localhost:8081, 추천 엔진 http://localhost:8001,
PostgreSQL 5433입니다. 그래서 두 스택을 동시에 띄워도 서로 방해하지 않습니다.

컨테이너 DB는 처음에 비어 있으므로 데모 데이터는 다음으로 넣습니다.

```bash
docker compose --profile seed run --rm seed
```

서비스별 설명, 포트를 밀어 둔 이유, `OPENAI_API_KEY` 넘기는 법, `scripts/demo-up.sh`와의 차이는
[docs/docker.md](docs/docker.md)에 정리해 두었습니다. 빠른 로컬 개발은 여전히 `scripts/demo-up.sh`가 편합니다.
