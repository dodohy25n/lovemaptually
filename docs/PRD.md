## 1. 문제

> **함께한 추억이 우리만의 데이터로 남지 않아, 매번 대중의 평가에 기대어 데이트 장소를 처음부터 다시 고민합니다.**

| | 문제 | 한 줄 요약 |
| --- | --- | --- |
| P1 | 기록의 파편화 | 사진·후기·위시리스트가 다른 앱에 흩어져, 함께 간 곳인데 함께 남지 않습니다 |
| P2 | 우리 둘의 평가 부재 | "우리한테 이 집은 몇 점인가"에 답할 데이터가 어디에도 없습니다 |
| P3 | 매번 0에서 시작 | 방문이 백 번 쌓여도 백한 번째 결정은 검색부터 다시 시작합니다 |
| P4 | 남의 기준에 기댄 선택 | 인기 있는 곳이 우리에게 맞는 곳은 아닙니다. 추천자의 취향이 우리와 얼마나 겹치는지 알 수 없습니다 |

기록이 남지 않으니(P1) 우리 둘의 기준이 만들어지지 않고, 기준이 없으니 결정을 매번 처음부터 다시 하며(P3), 그 빈자리를 익명 다수의 평가가 대신 채웁니다(P4).

그래서 **P2가 핵심입니다.** 이 서비스의 모든 데이터가 **커플이 아니라 개인 단위**로 들어가고, 합치는 일은 조회할 때만 하는 이유가 여기 있습니다.

## 2. 타깃과 페르소나

교제 6개월 이상, 월 2회 이상 함께 외출하며, 방문 장소를 사진으로라도 남기는 커플입니다. 기록 습관은 있지만 그 기록이 흩어져 있는 상태가 전제입니다.

**지민(27) · 도현(28) — 3년 차 커플**

주말마다 만나고, 장소를 정하는 쪽은 주로 지민입니다. 지민은 인스타그램 저장함에 가고 싶은 곳을 모으고 다녀온 뒤 대화방에 사진과 짧은 후기를 남깁니다. 도현은 따로 기록하지 않습니다.

### 장면 1 — 평소의 주말

저장해 둔 곳이 120개가 넘는데 오늘 갈 곳이 떠오르지 않고, 어떤 게 가 본 곳인지도 헷갈립니다. `P1`

지난달 파스타집을 지민은 좋았다고 기억하지만, 그날 도현은 웨이팅 40분에 지쳤습니다. **굳이 말할 일이 아니어서 어디에도 남지 않았습니다.** `P2`

결국 지도 앱 별점 4.5짜리를 추리는 것으로 돌아갑니다. 지난주에도 했던 그대로입니다. `P3`

### 장면 2 — 3박 4일 부산

여행 전날 밤 두 시간째 블로그를 읽습니다. 글쓴이의 취향이 우리와 얼마나 겹치는지 알 수 없습니다. `P4`

쌓아 둔 기록도 소용이 없습니다. **부산에는 가 본 곳이 하나도 없기 때문입니다.** `P3` `P4`

빈도는 낮지만 한 번의 아쉬움이 비교가 되지 않게 크고, 준비 시간도 몇 배입니다.

## 3. 해결 전략

**각자 리뷰를 남기면 AI가 취향을 읽어 내고, 다음에는 문장 한 줄로 물어봅니다.** 사용자가 하는 일은 별점 하나와 자유 문장뿐입니다. 태그를 고르게 하지 않습니다. 선택이 입력 부담이 크고, **선택지가 곧 취향의 상한**이 되기 때문입니다.

| 문제 | 해결 방식 | 기능 |
| --- | --- | --- |
| P1 | 그룹 단위 저장소. 장소·방문일·별점·리뷰가 한 흐름으로 묶입니다 | F2 F3 F5 |
| P2 | 취향을 **개인**에 저장하고 조회할 때 겹쳐 세 라벨로 나눕니다 | F4 F9 |
| P3 | 쌓인 취향을 붙여 **자연어 질의 한 줄**로 추천합니다 | F6 |
| P4 | 후보는 **실제로 커플들이 다녀와 평가한 곳**뿐입니다. 익명 다수의 평균이 아닙니다 | F6 F7 |

**설계 원칙 — 기록은 그 자체가 목적이 아니라 다음 결정의 입력입니다.** 사람에게는 편한 형태로 받되(자유 문장), 시스템 안에서는 셀 수 있는 형태로 바꿔 둡니다(태그).

## 4. 기존 대안과의 차별점

| 대안 | 남는 것 | 한계 |
| --- | --- | --- |
| 지도 앱 별점 | 익명 다수의 평균 | 우리 둘의 기준이 아닙니다 |
| 럽스타그램 | 남에게 보여줄 사진과 캡션 | **좋았던 것만 올라갑니다.** 어디를 피해야 하는지가 남지 않고, 검색할 수도 없습니다 |
| 메모 앱·대화방 | 각자의 텍스트 | 두 사람의 것이 하나로 합쳐지지 않습니다 |

> **럽스타그램은 앨범이고, 러브맵츄얼리는 데이터베이스입니다.**

## 5. 핵심 컨셉 — 취향은 개인에 쌓입니다

같은 리뷰 문장 하나가 **장소 쪽과 사람 쪽 두 곳**에 기록됩니다. 한 문장에 두 사실이 들어 있기 때문입니다.

> "창가 자리가 **조용해서 좋았다**"
> → **이 가게는 조용하다**(장소 정보)이면서 **나는 조용한 걸 좋아한다**(내 선호)

**AI가 태그마다 답을 두 개 줍니다** — `fact`는 **이 가게가 어느 쪽인가**, `want`는 **작성자가 어느 쪽을 원하는가**입니다.

| 리뷰 문장 | `fact` — 장소 쪽 | `want` — 사람 쪽 |
| --- | --- | --- |
| "웨이팅 40분이라 힘들었다" | 김 | 짧음 |
| "바로 들어갔다" | 짧음 | 짧음 |
| "매워서 좋았다" | 매움 | 매움 |
| "안 매워서 좋았다" | 순함 | 순함 |
| "너무 매워서 힘들었다" | 매움 | 순함 |

### 만족했는지를 묻지 않습니다

"만족했나" 하나만 받고 사실을 **뒤집어서** 짐작하고 싶은 유혹이 있습니다 — "불만이었다"를 뒤집으면 "웨이팅이 길었구나"가 나옵니다.

**이 뒤집기는 바람직한 방향이 모두에게 같은 속성에서만 성립합니다.** 웨이팅·청결·주차는 짧고 깨끗하고 편한 쪽이 만인에게 좋으므로 되짚을 수 있지만, **맵기·단맛·양은 좋은 방향이 사람마다 반대입니다.**

```
도현(순한 맛 선호) "안 매워서 좋았다"  ->  만족했음
지민(매운 맛 선호) "매워서 좋았다"      ->  만족했음
합치면: 맵기 만족 2   <-- 매운 집인지 순한 집인지 알 수 없습니다
```

둘 다 만족했지만 한 명은 안 매워서, 다른 한 명은 매워서 만족했습니다. **같은 숫자 안에 정반대의 사실이 들어가 뜻 자체가 성립하지 않습니다.** 이 상태로 추천 후보에 실려 나가면 매운 것을 못 먹는 사람에게 매운 집이 추천됩니다. **남의 평점을 쓰지 않겠다(P4)고 한 서비스가 자기 데이터로 틀린 정보를 만드는 셈입니다.**

그래서 만족도를 받지 않고 **답을 두 개 받습니다.** 위 두 리뷰는 장소 쪽에 `맵기 매움 1 / 순함 1`, 사람 쪽에 각각 `순함 1표`와 `매움 1표`로 남습니다. **둘 다 만족했는데 원하는 것이 반대라는 사실이 그대로 보입니다.**

### 취향이 갈린다는 것이 이 서비스의 정보입니다

한 장소에 구성원이 각자 리뷰를 쓰기 때문에 **원하는 쪽이 반대인 태그**를 잡아낼 수 있습니다. 만족도만 셌다면 도현의 "안 매워서 좋았다"와 지민의 "매워서 좋았다"가 둘 다 같은 값이 되어 이 갈림을 못 봤을 것입니다.

취향을 그룹 단위로 합쳐 저장했다면 `맵기`는 "우리 취향"으로만 남고 **지민이 못 먹는다는 사실이 사라집니다.** 데이터가 개인 단위인 이유가 이것입니다.

태그마다 구성원들의 판정을 겹쳐 **세 라벨** 중 하나로 보여 줍니다. S2 화면의 내용이 이 표입니다.

| 라벨 | 뜻 | 커플에서는 |
| --- | --- | --- |
| `ALL_SAME` | 판정된 사람이 전부 같은 쪽 | 둘 다 조용한 곳을 원함 |
| `ONE_SIDED` | 한 명만 판정됨 | 도현만 판정, 지민은 아직 근거가 얇음 |
| `SPLIT` | 서로 반대쪽 | 도현은 순한 맛, 지민은 매운 맛 |

**갈림(`SPLIT`)이 화면에 뜨는 순간이 이 서비스가 다른 추천 서비스와 갈리는 지점입니다.** 시연에서 그 한 장면을 반드시 보여 줍니다.

> 판정식·라벨 조건·집계 규칙은 [ERD.md](ERD.md)에, 그것이 추천에 어떻게 쓰이는지는 [추천시스템-설계문서.md](추천시스템-설계문서.md) 8장에 있습니다.

**취향이 갈릴 수 있는 태그는 여섯 개입니다** — `맵기` `단맛` `양` `조명` `넓이` `메뉴수`. 좋은 쪽이 사람마다 반대인 것들이고, 나머지 27개는 사실상 모두가 같은 쪽을 원합니다. **시연에서 갈림을 보여 주려면 이 여섯 중에서 골라야 하고**, `맵기`가 가장 직관적이라 데모 대본에 씁니다.

## 7. 후보의 정의 — 외부 리뷰를 가져오지 않습니다

추천 후보는 **우리 서비스 커플들이 실제로 다녀와 기록한 장소**뿐입니다. 블로그나 지도 앱의 리뷰를 끌어오지 않습니다.

P4를 푸는 서비스가 **남의 평점을 다시 데려오면 모순**입니다. 인터넷 전체를 검색하는 서비스가 아니고, 광고성 후기가 섞이지 않습니다. 지도 API는 장소를 검색하고 등록할 때만 쓰며 평점·리뷰는 가져오지 않습니다.

**초기 추천 품질이 낮다는 것을 인정합니다.** 기록이 없는 지역에서는 추천을 열지 않고 그 사실을 알립니다. 대신 **사용자가 늘수록 후보와 태그가 두꺼워지고 추천이 좋아집니다.**

> 콜드 스타트를 단계별로 어떻게 다루는지는 [추천시스템-설계문서.md](추천시스템-설계문서.md) 7장에 있습니다.

## 8. 범위 — 3일

**설계는 빠짐없이 합니다.** 3일 안에 코드로 만드는 것만 나눕니다. **Mock 경계는 LLM 호출에만 놓습니다.** 그 아래 DB 적재·취향 판정·후보 수집은 전부 실제로 동작합니다.

### 이번에 만드는 것

- **시스템 구조 다이어그램** — FE · BE · DB · 외부 시스템 사이의 데이터 흐름
- Use-Case 7건(UC-02 결번), **Wireframe 8장 전부**, [ERD](ERD.md), [REST API 명세](API-명세.md)
- FE / BE / DB Scaffolding — **단일 저장소**
- 핵심 화면 **두 줄기**의 End-to-End 검증
- 프롬프트 · 스키마 · 검증 로직

### 코드로 만드는 범위

명세는 7건 전부 쓰고, **End-to-End로 뚫는 것은 두 줄기 + 인증 + 월간 리포트**입니다.

| 화면 | 구현 | 이유 |
| --- | --- | --- |
| S1 리뷰 작성 | **E2E** | AI가 붙는 자리이고, 여기서 쓴 태그가 S3의 후보를 바꿉니다. 온보딩 첫 리뷰도 이 화면입니다 |
| S3 추천 | **E2E** | 규칙 해석 → 순위 → 이유 생성까지 전체 파이프라인을 보여 줍니다 |
| S2 우리 취향 | 조회만 | SQL 한 줄이라 여유가 있으면 붙입니다 |
| S7 가입·로그인 | **E2E** | 화면 때문이 아닙니다. `otherReviewsLocked`와 `403`이 서버의 요청자 식별을 전제하므로, 인증이 Mock이면 독립 평가를 시연할 수 없습니다(D-31) |
| S4~S6 (지도·연결·장소등록) | Wireframe만 | 명세와 화면 설계는 하되 코드로 만들지 않습니다 |
| S9 월간 리포트 | **E2E** | 유료 기능이자 실제 LLM이 붙는 유일한 자리입니다. 잠금 → Mock 결제로 해제 → 생성 → 열람이 한 화면에서 돕니다 |

**장소 검색(UC-03)은 시연 경로에서 뺍니다.** 카카오 로컬 API는 키 발급과 플랫폼 등록이 걸려 있어 데모 사고가 가장 잦은 지점이고, 장소가 이미 시드로 들어가 있어 나머지 흐름이 그것 없이 성립합니다. 명세·다이어그램·와이어프레임에는 그대로 남기고 연동만 R1로 미룹니다.

### 이번에 만들지 않는 것

- 실제 LLM 호출 — **모델 학습도 없습니다.** 리뷰 태그(AI-1)와 추천 이유(AI-2)는 Mock·템플릿입니다. **예외는 월간 리포트(AI-3) 하나**로, 여기만 실제 LLM을 호출합니다(§10 UC-08)
- 협업 필터링 새벽 배치 스케줄러 — 시드 데이터로 한 번 계산한 결과를 테이블에 미리 넣어 둡니다
- 소셜 로그인, 비밀번호 재설정, 리프레시 토큰, 로그아웃 블랙리스트, 권한 롤 (인증은 JWT 발급·검증과 BCrypt까지입니다)
- 사진 업로드와 스토리지 연동
- 배포·CI/CD, 알림·결제 — **결제 연동은 하지 않고 플랜 플래그와 Mock 결제로 표현합니다.** 그룹에 `FREE / PREMIUM` 플랜 값을 두고, "프리미엄으로 열기"를 누르면 실제 PG 대신 Mock 결제가 즉시 승인해 플랜이 바뀝니다. 언제부터 유료였는지는 남기되 카드·PG·정기 결제는 만들지 않습니다

### 비목표 — 기능을 늘릴지 판단하는 기준

- **관계 상담을 하지 않습니다.** 평가 데이터는 장소를 고르는 데만 쓰입니다.
- **소셜 리뷰 플랫폼이 아닙니다.** 다른 커플의 리뷰 원문과 정체는 노출되지 않고, 팔로우·좋아요는 만들지 않습니다.
- **사진 SNS가 아닙니다.** 기록의 목적은 보여 주는 것이 아니라 다음 결정입니다.

### 3일 완료 기준

- **S1 → S2 → S3 고리가 오류 없이 한 바퀴 돕니다.** 이것이 시연 경로입니다.
- 리뷰를 쓰면 태그가 붙고 장소 사실과 취향 집계가 갱신되어, **추천 후보가 실제로 바뀝니다.**
- 검증 로직이 Mock 상태에서도 그대로 동작합니다.
- 정의된 Use-Case 7건(UC-02 결번)이 모두 API 명세에 대응되고, **화면 여덟 장이 와이어프레임으로 존재합니다.**
- 월간 리포트가 FREE 그룹에서는 잠기고, Mock 결제로 열리며, 그 달 기록으로 리포트 한 편이 실제 LLM에서 생성되어 열람됩니다.
- 시스템 구조 다이어그램에서 AI 구현체를 가리키며 R1을 설명할 수 있습니다.

## 9. 핵심 기능

`범위` 열은 3일 안에 **코드로 만드는가**를 뜻합니다. 설계와 명세는 Must·Should 전부 씁니다.

| ID | 기능 | 우선순위 | 범위 | 문제 |
| --- | --- | --- | --- | --- |
| F1 | 회원가입 / 로그인 | Must | **E2E** | — |
| F2 | 그룹 만들기·참여 | Must | 설계만 | P1 P3 |
| F3 | 장소 검색 및 방문 기록 | Must | 설계만 | P1 |
| F4 | 별점 + 자유 리뷰 (**온보딩 겸함**) | Must | **E2E** | P1 P2 |
| F5 | 우리 지도 — 라벨별 핀 | Must | 설계만 | P1 P3 |
| F6 | 자연어 장소 추천 (Mock) | Must | **E2E** | P3 P4 |
| F7 | 리뷰 태그 자동 추출 (Mock) | Must | **E2E** | P2 P3 |
| F9 | **우리 취향 보기** — 세 라벨과 판정 근거 | Must | 조회만 | P2 |
| F12 | **월간 리포트** — 한 달의 기록을 AI가 글로 씁니다 (**유료**, PREMIUM) | Must | **E2E** | P1 P2 |
| F8 | 위시리스트 | Should | 설계만 | P3 |
| F10 F11 | 태그 필터, 추억 타임라인 | Could | 로드맵 | P1 P3 |

**온보딩 취향 설문은 별도 기능으로 두지 않습니다.** 태그 칩에서 고르게 하는 대신, 가입 직후 "먼저 가봤던 곳을 리뷰해 주세요"로 안내해 F4(리뷰 작성)를 그대로 재사용합니다. **화면 안내일 뿐 서버에는 온보딩 전용 경로가 없습니다** — 몇 건을 쓸지도 사용자가 정합니다(D-20).

**F12는 이 서비스의 수익화 지점입니다.** 한 달 동안 함께 다녀온 곳(리뷰·별점·라벨·갈린 태그·재방문)을 재료로 "우리의 한 달" 리포트를 씁니다. 숫자와 집계는 전부 서버가 세고, LLM은 문장만 씁니다. 리포트 안의 장소가 그 달 기록 밖을 가리키면 서버가 그 항목을 버립니다 — 추천에서 후보 밖 장소를 막은 것과 같은 원칙입니다. 기록이 쌓일수록 리포트가 두꺼워지므로, 유료 기능이 곧 "계속 기록할 이유"가 됩니다.

**F8은 테이블을 따로 두지 않습니다.** 장소 등록(UC-03)과 리뷰 작성(UC-04)이 별개 단계라 장소는 등록됐는데 라벨이 비어 있는 상태가 자연히 생깁니다. 나중에 "가고 싶은 곳" 기능을 만들면 그 상태를 그대로 쓸 수 있습니다. **다만 3일 범위에서 만드는 기능이 아니므로 그 상태를 위시리스트라고 부르지 않습니다** — 지금은 리뷰가 아직 없다는 뜻일 뿐입니다.

## 10. Actor와 Use-Case

### Actor는 둘입니다

| 이름 | 설명 | 관련 Use Case |
| --- | --- | --- |
| 사용자 | 서비스에 가입한 개인. 그룹에 속하면 함께 간 방문의 기록을 서로 봅니다 | UC-01, UC-03 ~ UC-08 |
| 지도 API | 외부 시스템. 장소 검색 결과와 place ID를 제공합니다 | UC-03 |

**"파트너"를 Actor로 두지 않습니다.** Actor는 특정 사람이 아니라 **역할**이고, 구성원들은 가입·리뷰·추천 요청·조회에서 하는 일이 완전히 같습니다. 파트너는 별도 역할이 아니라 **같은 Actor의 여러 인스턴스**입니다.

**"AI 추천 엔진"도 Actor로 두지 않습니다.** Use Case는 내부 구현을 숨긴 채 요청과 가시적 결과만 기술합니다. 사용자에게 보이는 것은 "물어보면 장소 목록이 나온다"이고, 그것이 모델인지 규칙인지는 보이지 않습니다. 그리고 **AI를 Actor로 올리면 "AI 없이는 시스템이 성립하지 않는다"는 뜻**이 되어 AI-Ready 주장과 모순됩니다.

| 외부 시스템 | 없으면 | Actor인가 |
| --- | --- | --- |
| 지도 API | **장소 등록 자체가 불가능.** UC가 죽습니다 | 예 |
| LLM | 추천이 규칙과 알고리즘으로 성립합니다. UC가 살아남습니다. 월간 리포트(UC-08)는 LLM이 없으면 생성이 실패 상태로 남지만, 기록·지도·추천은 그대로 돕니다 | 아니오 |

| ID | 이름 | 간단 설명 | Actor | 화면 |

| UC-01 | 그룹 참여 | 그룹을 만들어 초대 코드를 발급하거나, 받은 코드로 들어갑니다 | 사용자 | S5 |
| UC-03 | 장소 등록 | 지도에서 검색해 다녀온 장소를 우리 기록에 추가합니다 | 사용자 · 지도 API | S6 |
| **UC-04** | **리뷰 작성** | 별점과 문장을 남기고, 추출된 태그를 확인합니다. 온보딩 첫 리뷰도 같은 흐름입니다 | 사용자 | **S1** |
| UC-05 | 우리 취향 보기 | 세 라벨로 분류된 취향 표를 확인합니다 | 사용자 | **S2** |
| **UC-06** | **추천 요청** | 한 줄 질문을 보내고 장소 목록을 이유와 함께 받습니다 | 사용자 | **S3** |
| UC-07 | 우리 지도 조회 | 다녀온 곳을 라벨별로 지도에서 봅니다 | 사용자 | S4 |
| **UC-08** | **월간 리포트** | 한 달의 기록으로 "우리의 한 달" 리포트를 생성해 읽습니다. **유료(PREMIUM) 기능**입니다 | 사용자 | **S9** |

**UC-02는 결번입니다.** 원래 "태그 칩에서 좋아하는 것 5개·피할 것 3개를 고르는 온보딩 취향 입력"이었는데, UC-04(리뷰 작성)로 흡수했습니다(D-20). 칩 선택은 장소 쪽 데이터를 못 채웠고, 무엇보다 리뷰 작성이라는 화면·엔드포인트·AI 파이프라인이 이미 있는데 똑같은 일을 하는 별도 경로를 하나 더 두는 것이었습니다. 번호는 아이디일 뿐이라 결번을 메우려 뒤 번호를 당기지 않습니다.

가입·로그인(F1)은 UC로 세지 않고 S7로만 둡니다. 어느 서비스에나 있는 흐름이라 Use Case로 뽑아도 설계 판단이 생기지 않기 때문입니다.

**`include`·`extend` 관계를 쓰지 않습니다.** 일곱 개 중 두 곳 이상에서 공통으로 쓰이는 흐름이 없습니다.

**UC-04와 UC-06이 AI가 들어가는 두 지점이고, UC-08이 세 번째입니다.** 나머지 넷은 순수 CRUD이며 AI가 없어도 동작합니다. "AI가 빠지면 무엇이 안 되는가"의 답은 **"취향이 쌓이지 않고 추천이 성립하지 않습니다"**입니다. 세 지점의 역할은 다릅니다 — UC-04·UC-06에서 AI는 **고르지 않고 설명만** 하며, UC-08에서는 아예 고를 것이 없고 **쓰기만** 합니다. 그래서 UC-08만 3일 범위에서 실제 LLM을 붙입니다(§8).

### UC-04 명세 · 리뷰 작성

| 항목 | 내용 |
| --- | --- |
| Actor | 사용자 |
| Summary | 다녀온 장소에 별점과 자유 문장을 남기고, 시스템이 문장에서 읽어 낸 태그를 확인한다. |
| Precondition | 그룹에 속해 있고, 그 장소가 우리 기록에 등록되어 있다. |
| Post Condition | 리뷰가 저장되고, 장소 사실과 사용자 취향 집계가 갱신되었다. |
| Special Requirements | 다른 구성원의 별점과 리뷰는 본인이 그 장소에 리뷰를 남기기 전까지 노출되지 않는다. |
| UX Model | S1 리뷰 작성 화면 |

**Basic Flow**

1. 사용자는 시스템에게 리뷰 작성 화면을 요청한다.
2. 시스템은 장소 이름과 방문일이 채워진 리뷰 작성 화면을 보여준다.
3. 사용자는 별점을 선택하고 리뷰 문장을 입력한 뒤 저장을 요청한다.
4. 시스템은 리뷰를 저장하고 문장에서 태그를 읽어 낸다.
5. 시스템은 읽어 낸 태그를 화면에 보여주고, 장소 사실과 사용자 취향 집계를 갱신한다.
6. 시스템은 같은 장소에 리뷰를 남긴 다른 구성원의 리뷰를 함께 공개하고, 장소 라벨과 평가 인원 수를 표시한다.
7. 유스케이스는 종료한다.

**Alternative Flow**

```
1.1 가입 직후 첫 리뷰인 경우 (온보딩)
  1.1.1 시스템은 "먼저 가봤던 곳을 리뷰해 주세요"라는 안내를 함께 보여준다.
  1.1.2 이후 흐름은 기본 흐름과 같다. 별도의 화면이나 절차를 두지 않는다.

5.1 읽어 낸 태그가 없는 경우
  5.1.1 시스템은 리뷰를 정상 저장하고 태그 영역을 비운 채 보여준다.
  5.1.2 유스케이스는 종료한다.

6.1 아직 나 혼자만 리뷰를 남긴 경우
  6.1.1 시스템은 다른 구성원이 작성하면 함께 공개된다는 안내를 보여준다.
  6.1.2 라벨은 나 한 명을 분모로 계산해 "1명 평가"로 표시한다.
  6.1.3 유스케이스는 종료한다.
```

**Exception**

```
3.E 같은 장소·같은 날짜에 이미 리뷰를 작성한 경우
  3.E.1 시스템은 중복 작성임을 알리고 기존 리뷰 화면으로 이동한다.
        같은 장소라도 날짜가 다르면 재방문이므로 새 리뷰로 받는다.

4.E 태그를 읽어 내는 데 실패한 경우
  4.E.1 시스템은 리뷰만 저장하고 태그 영역을 비운 채 보여준다.
        리뷰 작성을 실패로 처리하지 않는다.
```

### UC-06 명세 · 추천 요청

| 항목 | 내용 |
| --- | --- |
| Actor | 사용자 |
| Summary | 한 줄 질문을 보내고, 그룹 구성원의 취향에 맞는 장소 목록을 이유와 함께 받는다. |
| Precondition | 그룹에 속해 있고, 구성원 중 최소 1명이 리뷰를 1건 이상 남겼다. |
| Post Condition | 추천 결과가 화면에 표시되었다. |
| Special Requirements | 추천 결과는 후보 목록 밖의 장소를 포함할 수 없다. |
| UX Model | S3 추천 화면 |

**Basic Flow**

1. 사용자는 시스템에게 추천 화면을 요청한다.
2. 시스템은 질의 입력창을 보여준다.
3. 사용자는 한 줄 질문을 입력하고 추천을 요청한다.
4. 시스템은 질문에서 지역·개수·예산을 읽어 낸다.
5. 시스템은 해당 지역에서 후보 장소를 모은다.
6. 시스템은 후보마다 점수를 매겨 순위를 정한다.
7. 시스템은 함께 가는 구성원 모두를 고려해 후보를 거르고 줄 세운다.
8. 시스템은 상위 후보에 이유 문장을 붙여 카드로 보여준다.
9. 유스케이스는 종료한다.

**Alternative Flow**

```
4.1 지역을 읽지 못한 경우
  4.1.1 시스템은 추천을 실행하지 않고 어느 동네인지 묻는 안내를 보여준다.
  4.1.2 사용자는 질문을 다시 입력한다. 흐름은 4단계로 돌아간다.

5.1 그 지역이 아직 추천 문턱에 못 미치는 경우
  5.1.1 시스템은 이 지역은 아직 추천이 열리지 않았다는 안내와 장소 등록 경로를 보여준다.
  5.1.2 유스케이스는 종료한다.

5.2 후보가 요청 개수보다 적은 경우
  5.2.1 시스템은 있는 만큼만 고르고, 후보가 부족했음을 함께 보여준다.

7.1 구성원 모두를 만족시키는 후보가 하나도 남지 않은 경우
  7.1.1 시스템은 거르는 조건을 완화해 상위 후보로 채운다.
        빈손으로 돌려보내지 않는다.

8.1 갈리는 태그가 붙은 장소를 고른 경우
  8.1.1 시스템은 이유에 누가 어느 쪽인지 함께 적는다.
```

**Exception**

```
1.E Precondition 미충족 — 그룹에 리뷰가 하나도 없는 경우
  1.E.1 시스템은 추천 화면 대신 "먼저 리뷰를 남겨 주세요" 안내와 리뷰 작성 경로를 보여준다.
        온보딩 리뷰(UC-04 1.1)로 이어진다.

8.E 이유 문장을 만들지 못한 경우
  8.E.1 시스템은 템플릿 문장으로 대체한다. 추천 자체는 실패로 처리하지 않는다.
```

> 각 단계가 내부적으로 어떻게 계산되는지는 [추천시스템-설계문서.md](추천시스템-설계문서.md) 11장 데이터 흐름에 있습니다.

### UC-08 명세 · 월간 리포트

| 항목 | 내용 |
| --- | --- |
| Actor | 사용자 |
| Summary | 한 달 동안 그룹이 함께 다녀온 기록을 재료로 "우리의 한 달" 리포트를 생성하고 읽는다. 유료(PREMIUM) 그룹만 생성할 수 있다. |
| Precondition | PREMIUM 플랜인 그룹에 속해 있고, 요청한 달에 그 그룹과 함께 간 리뷰가 1건 이상 있다. |
| Post Condition | 그 달의 리포트가 저장되어 그룹 구성원 모두가 열람할 수 있다. |
| Special Requirements | 리포트에 나오는 장소는 그 달 기록과 그 지역 후보 밖을 가리킬 수 없다. 리포트의 숫자와 집계는 시스템이 세고, 문장만 AI가 쓴다. 한 그룹은 한 달에 리포트 한 편만 갖는다. |
| UX Model | S9 월간 리포트 화면 |

**Basic Flow**

1. 사용자는 시스템에게 월간 리포트 화면을 요청한다.
2. 시스템은 그룹의 플랜을 확인하고, 지난 리포트 목록과 생성할 수 있는 달을 보여준다.
3. 사용자는 달을 고르고 리포트 생성을 요청한다.
4. 시스템은 그 달의 기록(방문 장소·별점·라벨·취향 태그·갈린 태그·재방문·전월 대비)을 집계한다.
5. 시스템은 접수 사실을 알리고, 집계를 재료로 리포트 문장을 생성한다.
6. 시스템은 생성된 리포트가 그 달 기록 안의 장소만 가리키는지 확인하고 저장한다.
7. 시스템은 제목·요약·이달의 장소·취향 변화·갈린 태그·다음 달 제안·맺음말을 화면에 보여준다.
8. 유스케이스는 종료한다.

**Alternative Flow**

```
2.1 그룹이 FREE 플랜인 경우
  2.1.1 시스템은 리포트 영역을 잠그고 "프리미엄으로 열기" 안내를 보여준다.
  2.1.2 사용자는 프리미엄 전환을 요청한다. 시스템은 Mock 결제를 승인하고 그룹 플랜을 PREMIUM으로 바꾼다.
  2.1.3 흐름은 2단계로 돌아간다. 결제 화면은 별도로 두지 않는다.

3.1 그 달의 리포트가 이미 있는 경우
  3.1.1 시스템은 새로 만들지 않고 기존 리포트를 연다.
  3.1.2 유스케이스는 종료한다.

6.1 생성된 리포트에 기록 밖의 장소가 섞인 경우
  6.1.1 시스템은 그 항목만 버리고 나머지로 리포트를 완성한다. 버린 개수를 함께 남긴다.

7.1 다른 구성원이 만든 리포트를 여는 경우
  7.1.1 리포트는 그룹의 것이므로 누가 요청했든 구성원 모두에게 같은 리포트를 보여준다.
```

**Exception**

```
3.E 그 달에 함께 간 기록이 하나도 없는 경우
  3.E.1 시스템은 리포트를 만들지 않고 그 달에는 쓸 기록이 없다는 안내를 보여준다.
        기록이 없으면 쓸 것이 없으므로 빈 리포트를 만들지 않는다.

5.E 리포트 문장을 만들지 못한 경우
  5.E.1 시스템은 리포트를 실패 상태로 남기고 다시 시도 버튼을 보여준다.
        템플릿 문장을 완성본으로 내주지 않는다. 유료 기능이라 완성본의 기준을 낮추지 않는다.
  5.E.2 사용자가 다시 시도하면 같은 리포트를 갱신한다. 새 리포트를 만들지 않는다.
```

> 입력 집계·프롬프트·출력 스키마·검증 규칙은 [추천시스템-설계문서.md](추천시스템-설계문서.md) 17장에, 결정 근거는 [설계결정.md](설계결정.md) D-34~D-41에 있습니다.

### 화면 — 여덟 장을 그리고 세 줄기를 뚫습니다

**Use Case 7건이 모두 화면을 가집니다.** 와이어프레임은 여덟 장 전부 그리고, 코드로 뚫는 것은 그중 셋입니다. 화면이 없는 Use Case가 있으면 그 흐름은 설계된 것이 아닙니다.

| 화면 | 이름 | UC | 구현 |
| --- | --- | --- | --- |
| **S1** | 리뷰 작성 (온보딩 첫 리뷰 겸함) | UC-04 | **E2E** |
| **S2** | 우리 취향 | UC-05 | 조회만 |
| **S3** | 추천 | UC-06 | **E2E** |
| S4 | 우리 지도 | UC-07 | 와이어프레임 |
| S5 | 그룹 만들기·참여 | UC-01 | 와이어프레임 |
| S6 | 장소 등록 | UC-03 | 와이어프레임 |
| S7 | 가입·로그인 | F1 | **E2E** |
| **S9** | 월간 리포트 (잠금·업그레이드·생성·열람) | UC-08 | **E2E** |

**S8은 결번입니다.** 작업지시서가 리포트 화면을 S9로 부르고 있어 그 번호를 그대로 썼고, UC-02와 같은 이유로 번호를 당기지 않습니다.

**화면 흐름**

```
S7 가입 ─→ S5 그룹 참여 ─→ S6 장소 등록 ─→ S1 리뷰 작성 ─┐  (온보딩: 먼저 가본 곳)
                                                        ▼
                     S4 우리 지도 ◀──────────────────── 홈 ──▶ S3 추천 ─┐
                          │                                          │
                          ▼                                          ▼
                     S6 장소 등록 ──────────────────▶ S1 리뷰 작성 ◀──┘  (추천받은 곳에 다녀와 리뷰)
                                                          │
                                                          ▼
                                                     S2 우리 취향
                                                          │
                                                          ▼
                                                     S9 월간 리포트  (한 달치 리뷰가 쌓이면)
```

**S1이 두 문맥에서 쓰입니다.** 가입 직후엔 온보딩으로, 추천받아 다녀온 뒤엔 평소 리뷰로 — 화면도 API도 완전히 같고 안내 문구만 다릅니다(UC-04 Alt Flow 1.1).

**S1 → S2 → S3이 하나의 고리를 이룹니다.** 리뷰를 쓰면 취향이 바뀌고, 바뀐 취향이 다음 추천을 바꾸고, 추천받아 다녀온 곳에 또 리뷰를 씁니다. **시연은 이 고리를 한 바퀴 도는 것으로 합니다.**

- **S1**은 저장 직후 읽어 낸 태그를 되돌려 보여 줍니다. AI가 무엇을 했는지 사용자가 확인하는 유일한 지점입니다.
- **S2**는 갈림 항목을 펼치면 각자의 횟수가 나오고, 라벨 옆에 **몇 명이 평가했는지**가 붙습니다.
- **S3**은 추천 이유와 근거 태그가 카드에 함께 붙어 **응답 스키마와 화면 요소가 1:1로 대응**합니다.
- **S9**는 한 화면에 네 상태가 있습니다 — FREE면 잠금과 "프리미엄으로 열기", PREMIUM이면 달 선택과 생성, 생성 중이면 스켈레톤, 완료면 리포트 본문. 실패하면 다시 시도 버튼이 같은 자리에 뜹니다. 리포트 본문의 일곱 구획(제목·요약·이달의 장소·취향 변화·갈린 태그·다음 달 제안·맺음말)이 출력 스키마와 1:1입니다.

**S4 우리 지도는 와이어프레임까지만 만듭니다.** 서비스 이름이 "맵"이라 발표에서 질문이 나오므로 화면 설계는 반드시 있어야 하지만, 지도 SDK 연동은 데모 사고가 가장 잦은 지점이고 그것 없이도 S1→S2→S3 고리가 성립합니다.

## 11. 확장 로드맵

**"나중에 한다"가 아니라 "이 숫자를 넘으면 한다"로 적습니다.** 왜 지금 넣지 않았는지에 대한 답이 됩니다.

| 단계 | 내용 | 착수 조건 |
| --- | --- | --- |
| R1 | LLM 실 연결 + 추천 배치 가동 | 즉시. 구현체 교체와 스케줄러 등록만 하면 됩니다 |
| R2 | 사전 확장 | 버려진 표현 로그를 집계해 **미매칭률 30% 초과** 시 축별로 태그를 추가합니다 |
| R3 | 추천 알고리즘 고도화 | **등록 장소 1,000곳 초과** 시 |
| R4 | 경량 분류 모델로 태그 추출 대체 | **월 리뷰 10,000건 초과** 시. 호출 비용이 문제가 되는 시점입니다 |
| R5 | 지역 확장 · 소규모 그룹 | 지역별 밀도가 확보된 뒤 |
| R6 | **맥락별 취향** — 업종·관계에 따라 취향을 나눠 셈 | **사용자당 평균 리뷰 30건 초과** 시 |
| R7 | **실제 PG 연동** — Mock 결제를 `PaymentClient` 구현체 교체로 실결제로 | **PREMIUM 전환 의사를 밝힌 그룹이 50쌍을 넘으면.** 그 전에는 결제 수단보다 가격(§12)이 먼저 정해져야 합니다 |
| R8 | **정기 결제·구독 만료 처리** — 월 단위 자동 갱신과 만료 시 잠금 | **유료 그룹 100쌍 초과** 시. 그 전에는 수동 전환으로 충분하고 만료는 `ended_at`만 채우면 됩니다 |
| R9 | **리포트 공유** — 리포트를 링크나 이미지로 그룹 밖에 내보내기 | **월 리포트 생성 500건 초과** 시. 그 전에는 공유가 아니라 생성 자체를 늘리는 것이 먼저입니다 |
| R10 | **프라이빗 LLM 교체** — 리포트 작성기를 Ollama 등 자체 호스팅 모델로 | **월 리포트 생성 2,000건 초과** 시(원가가 고정비를 넘는 시점) 또는 **리뷰 원문을 외부로 보내지 않는 것이 계약 조건이 되는 고객이 생기면.** `ReportWriter` 인터페이스 뒤 구현체 교체입니다 |

**R7~R10은 전부 월간 리포트(UC-08)에서 나옵니다.** 3일 범위에서는 결제를 `PaymentClient` 인터페이스 뒤 Mock으로 두고, 리포트 작성기도 `ReportWriter` 인터페이스 뒤에 둡니다. 그래서 넷 다 구조 변경이 아니라 구현체 교체입니다.

### 취향의 맥락 의존 — 알고 있는 한계입니다

**조용한 곳을 좋아하는 사람도 카페와 식당에서 원하는 바가 다를 수 있습니다.** 같은 사람이 친구와 갈 때와 가족과 갈 때 원하는 것도 다릅니다.

```
업종별   식당은 시끄러워도 괜찮지만 카페는 조용해야
관계별   친구랑은 시끄러운 데도 좋지만 가족이랑은 조용한 데
목적별   대화하러 갈 땐 조용한 곳, 작업하러 갈 땐 상관없음
```

지금은 **사람당 취향 하나**로 둡니다. 맥락을 넣으려면 데이터가 그만큼 쪼개져 판정에 필요한 최소 언급 횟수를 아무도 못 넘습니다. 차이를 만들어 놓고 그 차이를 보여 주지 못하는 것이 가장 아깝습니다.

**다만 재료는 이미 원본에 다 있습니다.** 각 태그가 어떤 업종·어떤 관계의 방문에서 나왔는지가 리뷰에 남아 있어, R6은 **과거 리뷰까지 소급해서 계산**할 수 있습니다. 기능을 켠 날부터 새로 모으는 것이 아닙니다.

**지금 안 넣는 것이 나중에 손해가 되지 않도록 원본을 설계해 둔 것**이고, 방문마다 누구와 갔는지를 남긴 이유가 여기에 있습니다.

**지표** — 커플당 월 리뷰 수 · 양측 리뷰 작성률 · 추천 결과 실제 방문 전환율 · 기록 없는 지역에서의 추천 채택률 · 사전 미매칭률
